# 排错

两张表。第一张按**状态码**查，第二张按**症状**查 —— 后者更常用，因为最难查的问题
恰恰是那些不报错的。

---

## 按状态码

| 码 | `error` 大意 | 真正的原因 / 怎么办 |
|----|-------------|-------------------|
| **400** | `map_name 不能为空`<br>`path 至少需要两个航点` | 请求体字段名写错了。是 `map_name` / `path`，**不是** `map` / `waypoints` |
| **401** | `未登录、令牌已过期或密钥无效` | 密钥拼错、已吊销、或过期。**注意它不区分这三种** —— 这是刻意的，避免泄露哪把密钥存在 |
| **403** | `无控制权限（viewer 只读）` | 用只读密钥做了写操作。要 operator 角色的密钥 |
| **403** | `该密钥为只读（leaseMode=none）…` | 角色够了但租约模式是 `none`。让管理员签发 `auto` 模式的 |
| **403** | `无权访问该机器人` | 密钥的范围不含这台机器人 |
| **404** | — | 别名 / 地图名 / 航点 ID 拼错。地图名带时间戳，重新建图后会变，别硬编码 |
| **409** | `机器人已被 xxx 控制，请先接管控制权` | 现场有人在操作，或另一个程序持有租约。等对方释放。响应里的 `holder` 告诉你是谁 |
| **409** | `请求正在处理中` | 同一个 `Idempotency-Key` 的首次请求还没返回。等一下再用**同一个键**重试 |
| **409** | `…先查任务状态` | 首次响应太大没能留存，无法安全重放。去 `GET /task` 看实际结果 |
| **429** | — | 触发限流（默认 5 请求/秒）。照响应头 `Retry-After` 退避，别硬重试 |
| **502** | `机器人不在线` | ①机器人断电/断网/agent 没起来；②**透传通道传了别名而不是机器人 ID** ← 很常见 |
| **502** | `隧道请求失败` | 请求发出去了但机器人端没回。机器人可能正在重启 |
| **503** | `机器人位置信息未就绪` | 还没做[重定位](full-patrol.md)，或定位没收敛 |
| **503** | — （访问 `/ssh`） | 管理员关掉了远程调试通道 |

## 按症状

### 任务下发返回 200，但机器人站着不动

**最常见的问题。** 按顺序查：

1. 漏了[第 ② 步启动设备](full-patrol.md)？没有它，导航模块根本没跑。
2. 漏了[第 ⑤ 步重定位](full-patrol.md)？机器人不知道自己在哪，不会动。
3. 急停指令还在下发？读 `/telemetry` 看 `data.emergency_active` —— 为 `true` 时
   机器人端在以 20Hz 持续下发停止指令，会和导航指令互相竞争。
   先取消急停（`POST /estop` 带 `{"active": false}`）。
4. `path` 里的航点属于另一张地图？航点 ID 在不同地图里会重复，不会报错但会走错。

### 轮询任务状态的循环永远不结束

你大概写了 `while status == 'running'`。**这个条件永远不成立** ——
下发时写 `running`，读回来是 `navigating`。失败时读回来是 `paused` 而不是 `failed`。

用集合判断，见[状态词表](api-reference.md#任务状态词)。

### 等定位就绪的循环永远不结束

你大概在轮询 `/perception` 等 `Location == 0`。**这个字段目前恒为 1**（机器人端
把 ROS 时间当 Unix 时间做新鲜度判断），哪怕定位完全正常。

改用 `telemetry` 的 `global_localization.received_at`，或者看 `/position` 是否从 503 变 200 ——
两种可靠做法都在 [api-reference.md](api-reference.md#判断定位是否就绪) 里。

### 重定位总是失败

先看你的 **HTTP 超时**。服务端会同步等定位算法收敛（最长约 20 秒），
客户端超时设成 10 秒会被自己掐断，报出来像「定位失败」。curl 加 `--max-time 60`。

超时够了还失败，就是 `node_id` 给的位置和机器人实际位置差太远，算法收敛不到。
换一个真实所在的航点。

### 同一个任务被执行了两次

重试时换了新的 `Idempotency-Key`，等于没做幂等。**重试必须复用同一个键。**

### 一切正常但读到的数据是旧的

看 `/telemetry` 的 `data.ros_available`。为 `false` 时机器人端 ROS 挂了，
接口还能返回，但内容是最后一次成功读到的陈旧值。

### 抓不到全景帧，也不报错

没加 `-rtsp_transport tcp`。UDP 在很多企业网里被丢包，表现就是干等。
见 [video.md](video.md)。

### 调了急停，机器人却没停

检查请求体。**必须是 `{"active": true}`** —— 发 `{}` 或 `{"active": false}` 是**取消**急停。
用 SDK 的 `bot.estop()` 就不会错（它已经带上 `active: true`）。

另外要理解急停的边界：它是让机器人端持续下发停止指令，**不是硬件急停、也不是一把锁**。
现场有人同时在遥控的话，两个指令源会互相竞争。要确保机器人绝对不动，按物理急停按钮。

### 我的控制权被人抢走了

正常行为。**现场登录的人可以抢走密钥持有的租约**，反过来不行 ——
这样现场操作员总能拿回一台正在自主跑动的机器人。
你的写操作会返回 409，等对方放手或重试即可。别试图靠高频写入抢回来。

### `auto` 密钥的租约怎么自己没了

`auto` 模式在你**停止写入约 30 秒后**自然释放，这是刻意的：
如果后台一直续期，高频调度会永久占锁，现场就再也拿不回机器人了。
下一次写操作会自动重新接管，你不用管。

## 自己先确认一遍

怀疑是自己代码的问题时，用这三条命令逐层排除：

```bash
# 1. 云端活着吗
curl -s "$CX_HOST/healthz"

# 2. 密钥有效、机器人在线吗
curl -s -H "X-API-Key: $CX_KEY" "$CX_HOST/v1/robots/$CX_ROBOT"

# 3. 机器人端接口通吗（读一个最简单的）
curl -s -H "X-API-Key: $CX_KEY" "$CX_HOST/v1/robots/$CX_ROBOT/telemetry"
```

三条都好 → 问题在你的请求内容（字段名、地图名、航点 ID）。
第 2 条 `online: false` → 机器人侧的问题，跟 API 无关。

## 报障时请提供

* 完整的请求（**去掉密钥**）与响应，含 HTTP 状态码
* 机器人别名，和 `GET /v1/robots/{别名}` 的输出
* 出问题的时间（带时区）—— 云端有审计日志，按时间能查到对应记录
